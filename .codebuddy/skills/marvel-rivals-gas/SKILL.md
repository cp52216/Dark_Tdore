## 一、GAS四大核心模块

### Ability（技能逻辑）
职责：技能入口层，负责技能生命周期管理
- 技能冷却（Cooldown）
- 技能激活条件判断
- 技能执行流程控制

### Task（技能行为）
职责：定义技能执行过程中的各种动作和状态变化
- 播放动画、执行移动、发射弹道、命中检测

### Effect（Buff/属性修改）
职责：对属性进行修改，管理状态关系
- 属性修改运算（加减乘除）
- 状态关系管理（互斥、覆盖、叠加）
- 持续性效果控制

### Cue（视听表现）
职责：技能的视听表现层（特效、材质、音效）

### 模块协作关系

```
Ability（技能激活）
    ↓ 调用
Task（执行行为：播放动画 / 检测 / 移动）
    ↓ 触发
Effect（属性修改：伤害 / Buff）
    ↓ 联动
Cue（视听表现：特效 / 音效）
```

## 二、数据配置系统的分层设计

### 三态拆分策略

**配置态一：AbilitySet（基础框架配置）**
- UI相关配置（图标、描述）
- 技能镜头表现
- 通用框架参数

**配置态二：AbilityConfig（技能特殊配置）**
- 每个技能拥有独立的配置结构体
- 适用范围：单个技能的个性化配置

**配置态三：AbilityPriority（技能关系配置）**
- 打断关系（A技能能否打断B技能）
- CD关系（共享CD、独立CD）
- 优先级设定

```
AbilitySet（框架级，所有技能共享）
    ↓ 继承
AbilityConfig（技能级，每个技能独立）
    ↓ 关联
AbilityPriority（关系级，技能间配置）
```

## 三、Buff系统的三层架构

```
第一层：Effect（战场共性元素）→ 正面/负面状态类型、属性修改方式
第二层：Buff（实体状态）→ 实例化系统行为
第三层：CDR（细粒度状态）→ Condition/Disable/Restrict
```

## 四、三大管线系统

### 检测管线（Detection Pipeline）

分层设计：全局配置 → Source配置 → Target配置 → 检测规则

四个执行步骤：
1. 收集来源信息（来源身上的状态、检测类型、阵营）
2. 确定检测规则（结合全局规则和来源配置）
3. 收集目标状态（目标的阵营、状态、特殊配置）
4. 应用通用规则（角度、距离、遮挡）

### 生成管线（Spawn Pipeline）

任何玩法、模式、活动都可以自定义英雄生成流程，核心逻辑通过配置驱动。

### 战斗数据管线（Combat Data Pipeline）

**效果器（Effector）**：对数据进行拦截、修改并记录。
- 运行时覆盖，无需修改原始配置
- 适合"同一英雄在不同模式下属性不同"的需求

## 五、客户端预测系统

### 为什么需要预测

解决网络延迟问题，保证游戏手感。

### 解决方案：客户端先行

```
客户端按下技能键
    → 客户端立即播放动画（先行）   ← 玩家无感知延迟
    → 同时发送请求到服务器         ← 后台进行
```

### 预测分类

| 类别 | 行为示例 | 是否预测 | 是否回滚 |
|------|----------|----------|----------|
| 可预测（必须预测） | 技能激活、位移、消耗（CD、能量） | ✅ | ✅ |
| 不可预测（相信服务器） | Buff控制效果、关键伤害和血量、变身 | ❌ | — |
| 可以不回滚 | 基础动画表现、一次性特效、发射的投射物 | ✅ | ❌ |

## 六、架构设计原则

| 原则 | 说明 |
|------|------|
| 模块化与可扩展性 | 每个系统高度模块化，可独立扩展 |
| 配置驱动 | 将逻辑转化为配置，减少硬编码 |
| 分层抽象 | 多层架构保持灵活性的同时控制复杂度 |
| 管线化思维 | 将复杂业务流程标准化为管线 |
