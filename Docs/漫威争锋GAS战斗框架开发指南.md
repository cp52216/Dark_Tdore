## 一、GAS四大核心模块

GAS（Gameplay Ability System）是UE官方提供的技能系统框架，由四大核心模块组成：

### 1.1 Ability（技能逻辑）

**职责：** 技能的入口层，负责技能生命周期管理

- **技能冷却（Cooldown）**：控制技能的使用间隔
- **技能激活条件判断**：判断技能当前是否可以使用（资源够不够、状态是否允许）
- **技能执行流程控制**：管理技能从激活到结束的完整流程

### 1.2 Task（技能行为）

**职责：** 定义技能执行过程中的各种动作和状态变化

- 播放动画
- 执行移动
- 发射弹道
- 命中检测
- 等待事件回调

> **开发要点：** Task是GAS中扩展性最强的部分，复杂技能的差异性主要体现在Task的组合方式上。

### 1.3 Effect（Buff/属性修改）

**职责：** 对属性进行修改，管理状态关系

- **属性修改运算**：加、减、乘、除
- **状态关系管理**：互斥、覆盖、叠加
- **持续性效果控制**：Duration、Period等时间控制

### 1.4 Cue（视听表现）

**职责：** 负责技能的视听表现层

- 特效播放（Niagara）
- 材质变化
- 音效呈现

### 1.5 模块协作关系

```
Ability（技能激活）
    ↓ 调用
Task（执行行为：播放动画 / 检测 / 移动）
    ↓ 触发
Effect（属性修改：伤害 / Buff）
    ↓ 联动
Cue（视听表现：特效 / 音效）
```

## 二、技能执行流程

以刀锋的一个简单技能为例，完整执行流程如下：

| 步骤 | 所在层 | 动作 |
|------|--------|------|
| 1 | Ability层 | 技能激活，判断技能是否可以使用 |
| 2 | Task层 | 播放动作（动画蒙太奇） |
| 3 | Task层 | 检测目标（命中判定） |
| 4 | Effect层 | 作用伤害（通过Effect对目标造成伤害） |
| 5 | Cue层 | 播放表现（命中特效、音效） |

> **开发要点：** 这个流程是GAS的标准执行链路，所有技能都遵循"激活→行为→效果→表现"的链式调用。理解这条链路是开发任何技能的基础。

## 三、GAS之外的拓展系统

《漫威争锋》在GAS基础上构建了四大拓展系统，以应对GAS原生功能无法覆盖的需求：

| 拓展系统 | 解决的问题 |
|----------|-----------|
| 数据配置系统 | GAS原生配置能力不足，需要分层配置支持复杂技能 |
| 技能逻辑扩展 | 复杂技能逻辑（传送门、磁场吸收）无法用标准Task实现 |
| 表现系统优化 | 原生Cue功能有限，需要中间层抽象和反向调用能力 |
| 基建模块开发 | 检测管线、生成管线等框架级基础设施 |

> **开发要点：** 不要试图用GAS原生功能解决所有问题。当需求复杂到一定程​​度时，在GAS之上构建拓展系统是正确的工程决策。

## 四、数据配置系统的分层设计

### 4.1 三态拆分策略

将技能配置拆分为三个独立的配置态，各司其职：

**配置态一：AbilitySet（基础框架配置）**

- UI相关配置（图标、描述）
- 技能镜头表现
- 通用框架参数
- 适用范围：所有技能共享的框架级配置

**配置态二：AbilityConfig（技能特殊配置）**

- 钢铁侠的飞行系统配置
- 刀锋的普通攻击配置
- 每个技能拥有独立的配置结构体
- 适用范围：单个技能的个性化配置

**配置态三：AbilityPriority（技能关系配置）**

- 打断关系（A技能能否打断B技能）
- CD关系（共享CD、独立CD）
- 优先级设定（同时触发时谁先执行）
- 适用范围：技能间的横向关系管理

### 4.2 设计原则

```
AbilitySet（框架级，所有技能共享）
    ↓ 继承
AbilityConfig（技能级，每个技能独立）
    ↓ 关联
AbilityPriority（关系级，技能间配置）
```

> **避坑：** 不要用单一配置表承载所有技能数据。单一配置表会导致字段爆炸、维护困难、无法差异化配置。

## 五、AbilityTask的深度扩展

### 5.1 Task的执行流程

```
技能激活（Ability）
    ↓
播放行为（Task）—— 可能非常复杂
    ├── Timeline时间轴动画
    ├── 枪线射击逻辑
    ├── 冲刺移动
    └── 各种技能机制
```

### 5.2 技能模板系统

对于有共性的技能类型，使用标准化模板提升开发效率：

**枪线类技能模板**标准化流程：
1. 播放时间轴动画
2. 发射弹道
3. 命中判定

其他标准化模板：
- 二段跳模板
- 飞行模板
- 变身模板

### 5.3 方案选型对比

| 方案 | 优势 | 劣势 | 适用场景 |
|------|------|------|----------|
| 逐个配置Task | 灵活性高，每个技能可完全定制 | 开发效率低，维护成本高 | 完全独特的技能（传送门、磁场吸收） |
| 技能模板系统 | 开发效率高，复用性强，一致性好 | 灵活性受限 | 有共性的技能类型（枪械、移动、变身） |

> **开发要点：** 实际项目中两种方案混合使用。独特技能用独立Task，通用技能用模板系统。先用模板覆盖80%的技能，再用独立Task处理20%的特殊情况。

## 六、技能时间轴系统（Timeline）

### 6.1 Timeline与动画蒙太奇的区别

这是一个关键的职责分离设计：

| 维度 | Timeline | Animation Montage |
|------|----------|-------------------|
| 核心职责 | 控制**逻辑流程**和**时间节点** | 控制**动画播放**和**骨骼动画混合** |
| 管理内容 | 技能阶段划分（前摇、生效、后摇） | 骨骼动画片段 |
| 触发内容 | 关键帧事件（伤害判定、特效、音效） | 动画通知（AnimNotify） |

### 6.2 Timeline的精确控制能力

- 技能各阶段的持续时间
- 伤害判定的精确时机
- 特效播放的时间点
- 音效触发的节点

```
Timeline时间轴示例：
|----前摇----|----生效----|----后摇----|
     0.2s         0.1s         0.3s
                   ↑
              伤害判定点
              特效触发点
```

> **开发要点：** 将逻辑时间轴与动画分离，是大型项目的标准做法。这样即使动画资源更新，逻辑时序不受影响；反之亦然。

## 七、Buff系统的三层架构

### 7.1 三层结构设计

```
第一层：Effect（战场共性元素）
    ↓ 被引用
第二层：Buff（实体状态）
    ↓ 细化
第三层：CDR（细粒度状态）
```

**第一层：Effect（战场共性元素）**

- 正面/负面状态类型定义
- 属性修改方式（加、减、乘、除）
- 状态之间的互斥关系
- 类似GAS原生GameplayEffect的角色

**第二层：Buff（实体状态）**

- 引用Effect的共性元素
- 实例化系统行为
- 示例：女巫的"虚无"状态——Effect定义共性效果，Buff实例化"不可选取"等系统行为

**第三层：CDR（细粒度状态）**

- **C**ondition：条件限制
- **D**isable：禁用控制
- **R**estrict：特殊限制
- 示例：不能移动、不能跳跃、特殊状态的具体实现

### 7.2 三层架构的优势

| 优势 | 说明 |
|------|------|
| 结构清晰 | 每一层职责明确，Effect管共性，Buff管实例，CDR管细节 |
| 扩展性强 | 新增Buff类型可复用底层Effect逻辑 |
| 配置简化 | 策划只需关注Buff层配置，无需理解底层细节 |

> **开发要点：** 这三层不是GAS原生结构，而是《漫威争锋》在GAS Effect之上的扩展架构。如果你的项目Buff类型多、关系复杂，建议参考这种分层方式。

## 八、表现系统与Gameplay Cue的扩展

### 8.1 TypedCue中间层架构

在业务逻辑层和底层表现之间增加TypedCue中间层：

```
业务逻辑层（Ability / Task）
    ↓ 触发
TypedCue中间层（共性行为抽象）
    ↓ 传递
Niagara / SkeletalMesh（底层表现）
```

**TypedCue抽象的共性行为：**
- 控制特效激活/结束时机
- 传递参数到Niagara
- 管理特效生命周期

### 8.2 Data Interface：Niagara反向调用Game逻辑

**方向一：Cue Data（标准传参，Game → Niagara）**

- 传递曲线数据到Niagara
- 实现弹道弹出效果
- 特效挂载到角色特定部位

**方向二：Data Interface（反向调用，Niagara → Game）**

| 应用场景 | 工作方式 |
|----------|----------|
| 低血量特效 | Niagara直接读取角色血量，根据阈值自动切换 |
| 霸体表现 | Niagara直接查询角色是否处于霸体状态 |
| 平台状态 | 动态读取平台相关信息 |

> **开发要点：** Data Interface反向调用让特效系统具备"感知游戏状态"的能力，避免了在Game逻辑中频繁更新特效参数。适合需要根据状态实时变化的持续型特效。

## 九、三大管线系统

### 9.1 检测管线（Detection Pipeline）

**问题场景：** 法阵检测从简单的地面范围检测，演变为需要支持自定义响应、屏蔽特定类型、反弹检测等，形成M对N的复杂关系。

**分层设计：**

| 层级 | 说明 | 配置内容 |
|------|------|----------|
| 全局配置 | 玩法模式级 | 检测开关（如队伤）、模式级规则覆盖 |
| Source配置 | 检测发起方 | 投射物、法阵、枪线等的检测类型和规则 |
| Target配置 | 被检测方 | 角色、召唤物、场景元素的"被检测规则" |
| 检测规则 | 检测类型定义 | 法阵/弹道检测类型标签、优先级和互斥关系 |

**四个执行步骤：**

```
1. 收集来源信息
   → 来源身上的状态、检测类型、阵营等

2. 确定检测规则
   → 结合全局规则和来源配置，确定collision和mask

3. 收集目标状态
   → 目标的阵营、状态、特殊配置

4. 应用通用规则
   → 角度、距离、遮挡等最终判定
```

**核心优势：** 扩展性、可维护性、灵活性、安全性

> **开发要点：** 不要在技能配置中硬编码检测逻辑。检测逻辑应独立为管线系统，通过配置驱动。当新增检测需求时，只需增加配置项而非修改代码。

### 9.2 生成管线（Spawn Pipeline）

**核心问题：** 如何在不同游戏模式下生成英雄？

**设计思路：**
- 增加生成管线层，重建整个战斗英雄的信息
- 任何玩法、模式、活动都可以自定义英雄生成流程
- 核心逻辑通过配置驱动，而非硬编码
- 支持对英雄的血量、技能、属性进行全方位定制

### 9.3 战斗数据管线（Combat Data Pipeline）

**核心概念：效果器（Effector）** —— 对数据进行拦截、修改并记录

**工作原理：**

```
1. 模式定义效果器
   → 每个模式可以为特定英雄配置效果器

2. 策划配置数据覆盖
   → 在效果器中配置需要修改的数据

3. 拦截底层访问
   → 当程序访问战斗数据时，效果器拦截并返回修改后的值
```

| 优势 | 说明 |
|------|------|
| 灵活性 | 运行时覆盖，无需修改原始配置 |
| 安全性 | 不修改原始配置数据 |
| 可追溯性 | 所有修改都有记录，便于调试 |

> **开发要点：** 效果器模式非常适合"同一英雄在不同模式下属性不同"的需求。效果器配置应有明确的优先级和覆盖规则。

## 十、战斗实体系统

### 10.1 三大战斗实体类型

| 类型 | 特点 | 典型应用 |
|------|------|----------|
| 投射物（Projectile） | 延迟弹道、飞行轨迹计算、碰撞检测 | 子弹、火球、飞行道具 |
| 法阵（Field） | 大范围检测、持续性效果、区域控制 | 治疗圈、毒雾、传送门 |
| 召唤物（Summon） | 拥有生命值、可释放技能、有独立AI | 宠物、分身、炮台 |

### 10.2 实体组合机制

实体之间可以相互组合，形成复合技能效果：

```
组合示例：
- 投射物携带法阵    → 子弹落地后生成范围伤害区
- 投射物携带召唤物  → 投掷物落地后生成宠物
- 召唤物释放投射物  → 炮台自动发射子弹
```

### 10.3 实体管理系统职责

- 生命周期管理（创建、更新、销毁）
- 网络同步（服务器与客户端状态一致）
- 碰撞检测
- 性能优化（对象池、LOD等）

## 十二、客户端预测系统

### 12.1 为什么需要预测系统

**核心作用：解决网络延迟问题，保证游戏手感。**

### 12.2 问题分析：CS架构的天然延迟

传统流程（有问题）：

```
客户端按下技能键
    → 发送请求到服务器        ← 网络延迟
    → 服务器处理逻辑          ← 处理时间
    → 服务器返回结果          ← 网络延迟
    → 客户端播放动画          ← 玩家感知到卡顿
```

### 12.3 解决方案：客户端先行

优化后流程：

```
客户端按下技能键
    → 客户端立即播放动画（先行）   ← 玩家无感知延迟
    → 同时发送请求到服务器         ← 后台进行
    → 服务器确认                  ← 后台进行
```

### 12.4 UE的预测窗口机制

**两个核心模块：**

| 模块 | 说明 |
|------|------|
| 预测窗口（Prediction Window） | 在战场构建预测逻辑，通过Scope的创建和销毁决定预测的生命周期 |
| 预测器（Prediction Key） | 这段预测逻辑的唯一标识，用于客户端和服务器之间的对应关系 |

### 12.5 预测流程详解

**客户端侧流程：**

```
1. 创建预测窗口
2. 使用技能（扣除资源：CD、能量）
3. 直接播放动画
4. 将预测Key发送给服务器
```

**服务器侧流程：**

```
1. 接收到预测Key
2. 尝试使用技能
3. 创建预测窗口并激活
4. 播放动画
```

**两种结果：**

| 情况 | 服务器结果 | 客户端行为 |
|------|-----------|-----------|
| A | 激活成功 | 预测成功，流程正常完成 |
| B | 激活失败（被眩晕、CD不足、条件不满足） | 服务器将预测Key发回客户端，告知需要回滚 |

### 12.6 预测窗口的回滚机制

```
技能阶段：准备阶段 → 生效阶段 → 结束阶段

如果生效阶段预测失败：
1. 停止当前阶段的执行
2. 回滚已经发生的效果
3. 恢复到预测前的状态
```

### 12.7 可预测行为与不可预测行为

**判断标准：是否影响手感？**

| 类别 | 行为示例 | 原因 |
|------|----------|------|
| **可预测（必须预测）** | 技能激活、位移、消耗（CD、能量） | 直接响应玩家输入，必须立即反馈 |
| **不可预测（相信服务器）** | Buff控制效果（冰冻、眩晕）、关键伤害和血量修改、变身 | 回滚成本太高或无法回滚 |
| **可以不回滚** | 基础动画表现、一次性特效、发射的投射物、瞬时弹道 | 生命周期短，或已成既定事实 |

### 12.8 需要回滚的关键逻辑

- **技能激活**：服务器不允许，必须取消
- **冲刺和位移**：预测错了要拉回来（"拉回"表现）

### 12.9 预测系统的实际效果

- 200ms延迟和10ms延迟下，**技能激活流程完全一致**
- 快速位移攻击技能即使在200ms延迟下，与10ms延迟几乎没有差异

### 12.10 预测失败的真实案例

**场景：** 刀锋开大招冲刺，过程中被冰霜女巫的冰冻打断

- 从冰霜女巫视角：她并没有看到刀锋开大招
- 刀锋预测了冲刺行为，但服务器判定冰冻生效，应打断大招
- **预测失败不代表错误**，它是游戏中正常的公平性规则

### 12.11 预测系统黄金法则

```
✅ 预测影响手感的操作（激活、位移、消耗）
❌ 不预测难以回滚的操作（变身、伤害、控制）
🔄 对于可回滚的操作，提供流畅的回滚表现
⚖️ 预测失败是保证公平性的必要代价，而非BUG
```

## 十三、架构设计原则与避坑指南

### 13.1 架构设计核心原则

| 原则 | 说明 | 体现 |
|------|------|------|
| 模块化与可扩展性 | 每个系统高度模块化，可独立扩展 | 技能系统、Buff系统、检测管线 |
| 配置驱动 | 将逻辑转化为配置，减少硬编码 | 三态技能配置、效果器、技能模板 |
| 分层抽象 | 多层架构保持灵活性的同时控制复杂度 | Buff三层架构、Cue中间层设计 |
| 管线化思维 | 将复杂业务流程标准化为管线 | 检测管线、生成管线、战斗数据管线 |

### 13.2 配置系统避坑

- **避免**使用单一配置表承载所有技能数据
- **不要**在技能配置中硬编码检测逻辑
- **确保**效果器配置有明确的优先级和覆盖规则

### 13.3 预测系统避坑

- **确保**预测失败的回滚彻底，不能有遗留状态
- **不要**预测有副作用且难以回滚的操作
- **严格**保证预测Key的生成和匹配逻辑

### 13.4 性能优化避坑

- **注意**检测管线的性能优化，避免过度碰撞检测
- **使用**对象池和LOD机制管理特效系统
- **及时**清理预测系统的窗口，避免内存泄漏
